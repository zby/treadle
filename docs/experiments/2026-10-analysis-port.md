# Porter C: code-base analysis (steps 2-9) as a portable Monty script

> **Historical experiment.** Prototype commands and recorded output are retained
> as measured, not current CLI instructions. Use `treadle` for the implemented
> runner; see [Running Treadle](../RUNNING.md).

## What I ran

    cd experiment && uv run python analysis/check.py     # type check + 3 scenarios + failure + step-replay simulation

Files (all in `analysis/`): `analysis.py` (script), `catalog.py` (11 agents), `check.py` (harness), `stubs.pyi`
(generated by check.py: the stubs fed to Monty's type checker). Nothing outside `analysis/` and this file was touched.

Harness facts (measured): the stubs use the same recipe as `_build_type_check_stubs`
(`FunctionSignature.from_schema` from each agent's JSON schema, `TypeAdapter(...)` for unions), and are fed via
`pool.checkout(type_check=True, type_check_stubs=...)` on `AsyncMonty` (pydantic-monty 1.1.0 `_monty.pyi`; I use
`feed_run` with `inputs=` and `external_lookup=` of async functions). The checker rejected 2 of 3 deliberately broken
scripts (misspelled TypedDict key: `invalid-key`; unknown agent name: `unresolved-reference`). It did NOT reject a
positional `call(make_task(...))`, because the helper `job(label, call, ...)` takes `call` untyped. That one is
caught only at runtime (DynamicWorkflow's dispatch raises TypeError).

Scenarios, all passing type check and finishing in Monty with a deterministic content-based fake (answers depend on
the prompt text, not on call order, so replays are stable):
- `full`: 19 agent calls. One boundary retry (first boundary has `../outside`, rejected by the in-script check, retried
  with the failure text; manifest shows boundary attempt 2). One refusal (the epistemic analyst refuses; the verifier is
  told by a structural finding, requests a rewrite; epistemic version 1). One correction round (memory also requested).
  Reconciliation and verification run twice. Profile and synthesis accepted first try. Result `outcome: accepted`,
  manifest of 8 members with attempt, version, refused.
- `problem`: verifier returns `problem`; result `outcome: problem` after 8 calls, nothing downstream runs.
- `out_of_scope`: boundary refusal; 1 call; `outcome: out-of-scope`.
- Out of attempts (boundary never valid): script raises `RuntimeError: boundary: out of attempts after 2: [...]`.
- Step replay simulation (an unanswered call never returns; `wait_for` timeout = "all branches blocked"): 17 steps,
  19 distinct keys. Step 3 posts only `runtime_analyst`; step 4 posts memory, epistemic and workflow together.

## Answers

### 1. Does the whole workflow fit the subset?

Yes. I wanted nothing Monty rejected; every construct I used type-checked and ran. This is a negative result for
the question "what does Monty reject", and I only probed what I needed. Constructs I used or probed on purpose and that
work: top-level `await` and `async def`; nested `async def` closures; `asyncio.gather(*[... for ...])`; passing external
agent functions as first-class values (`job(..., call=report_verifier)`) and in a dict (`ANALYSTS[role](task=...)`);
lambdas as arguments; f-strings, `str.format`, `"\n".join`, `sorted`, `enumerate`, comprehensions, dict comprehension,
`for/else`, `try/except RuntimeError`, `re`, `json`, `dataclass` (probe only, not used); `raise RuntimeError`;
TypedDict narrowing on a required `Literal` field (`if out["kind"] == "refusal"`); annotations naming stub types
(`r: Report`), which are type-checked but not evaluated at runtime (tested without type check: they run).
Not probed: generators, classes with inheritance (not needed).
Things that cost me design effort rather than being rejected:
- Optional fields. A Pydantic field with a default becomes `NotRequired` in the stub, which forces `.get()`. I made
  every field required in `Verdict` (`requests`, `problem: str | None`).
- Refusal variant needs a discriminator. `Report | Refusal` renders as a union of TypedDicts; narrowing works only if
  `kind` is a required `Literal` in each member. With a default (`kind: Literal[...] = "report"`) it renders
  `NotRequired` and I did not rely on narrowing there.
- Type checking only covers typed code. Helpers with unannotated parameters are `Any`, so the misspelled-key test was
  first missed; annotating check functions with the stub type names (`Report`, `Boundary`, ...) fixed that. A script
  author has to know to do this. The stubs' type names thereby become part of the script's contract.
- Runner inputs are not known to the checker; I appended `system: str` etc. declarations to the stubs
  (`INPUT_DECLS`). DynamicWorkflow has no inputs, so the runners need the same trick or a `skip_type_check`.

### 2. What had to leave the script, and why

Left the script (host or runner side):
- Step 1 acquisition and publication (by the task statement). The checkout is read by the agents themselves, not the script.
- The boundary file-system check. The script cannot touch files. Workaround: acquisition passes `source_files`
  (tracked file list) as an input; the check `inside_source` is then pure (no `..`, not absolute, path or prefix of a
  listed file). What cannot be done this way: symlink escapes, content/size checks, anything needing the bytes.
  The input also has to be trustworthy: it is not in any key, so a different listing silently changes check results on replay.
- Schema validation: done by the runner against the output type (Pydantic) before the script sees the dict. The
  script sees only already valid dicts, so its "checks" are the run's rules (non-empty, cited paths inside the
  boundary, verdict consistency), not schema checks.
- Which worker profile and model produced each result: the script can only record its own attempt number. It cannot
  know about runner-level retries (e.g. Pydantic AI output-validation retries). Needs completion records in the runner.
- Time: nothing needed it. No clock, no random, no sleep in the script.
- Out-of-attempts stop-for-operator: the script can only `raise RuntimeError`; the run-level meaning ("stopped, operator
  decides", resumable) is the runner's.

Stayed in the script as pure Python (about 85 lines, `analysis.py` lines 23-108): boundary check, report check
(length, answers file present, evidence cited, cited paths inside the boundary), profile check, reconciliation check
(two distinct known roles, prevented conclusion present), the structural check over boundary + four reports +
reconciliation (including refused reports), verdict consistency (accepted has no requests; rejection names a target;
every structural failure that names a role has an explicit request; no unknown targets), assembly of overview and
manifest. None needed a library. A real structural check that parses markdown or resolves links across documents might
need `re` (available) but not more; I did not write one of that depth, so this is an expectation.

### 3. Wait without reading

Expressed as plain sequencing:

    reports = {"runtime": await analyst_job("runtime", ...)}
    rest = await asyncio.gather(*[analyst_job(r, ...) for r in ROLES[1:]])

The three tasks do not mention the runtime report, so their text is exactly what it would be without the wait. No
prompt text changed, the key does not contain the runtime report, and no new language feature (`after=`) was needed.
Measured in the replay simulation: step 3 posts only runtime, step 4 posts the other three together.
Limits (stated, not hidden): (a) it is ordering only; nothing prevents an analyst from reading the runtime report if it
sits in the checkout/working area, so "does not read" remains an instruction. (b) The three analysts do not run
concurrently with runtime, which matches the spec. (c) Because the dependency is not in the key, re-answering runtime
would not invalidate the other three (same in the earlier sketches, where `after()` kept it out of the key too).

### 4. Where retries, refusals and `problem` live; readability; line counts

- Retries with failure feedback: one helper `job(label, call, make_task, check, limit)`; the failures are rendered into
  the task text (`failure_text`), so each attempt has a new key. Attempt limits: boundary 2, others 3, synthesis 2
  (loop in `verified_synthesis`). Out of attempts: `raise RuntimeError`.
- Refusals: `job` returns `{"attempt", "refused": True, "value": refusal}` without retry and without running the check.
  `show()` renders it as `REFUSED. Reason: ...` into later prompts, so verifiers read it; a structural finding forces
  an explicit request for a refused report. A refusal by the boundary agent gives `out-of-scope`; by the verifiers,
  profile or synthesis agents gives `blocked` (my reading of the spec; the spec only says `blocked` and `out-of-scope` exist).
- `problem`: a field of `Verdict`; the script checks it right after the verdict and returns
  `{"outcome": "problem", ...}`. Same for the profile/synthesis verifiers.
- Spec gaps I had to decide (flag for the owner): retry counts for the profile and the report verifier; what a late verifier
  (profile/synthesis stage) does if it asks for a report correction (I only allow its own target); synthesis verifiers
  short-circuit on the first rejection; maximum correction rounds (3).
- Readability: control flow reads top to bottom, close to the sketch in STEP-PROGRAMS.md (boundary; analysts;
  loop over rounds with `reconcile`/`structural`/`verify`/`correct`; profile; synthesis; assemble). It is longer than
  the earlier sketches because it covers steps 7-9, refusals, deterministic checks inline, and prompt text. The weak
  spot is the many return-a-dict "outcome" exits and the `for ... else` with `break` in the round loop.

Line counts (physical / non-blank non-comment):
- `analysis/analysis.py` (this port, steps 2-9 + refusals + checks + prompts): 326 / 263
- `scratch/workflows/analysis.py` (steps 1-6 + publish, no refusals, no 7-9, checks in `shared.domain`): 125 / 83
- `luigi/workflows/analysis.py` (same scope as scratch): 245 / 178
- Supporting here: `catalog.py` 119 / 92; `check.py` 203 / 167.
Not apples to apples: the earlier sketches import their checks from `shared.domain` (not counted) and omit steps 7-9.
About 85 of my 263 lines are the checks that the sketches kept outside. Without them, and without steps 7-9 and
refusals, the control flow would be roughly the size of the scratch sketch (expectation, not measured).

### 5. Prompt size

Yes, large. Verification prompts embed the boundary, all four reports (report text + answers file), the reconciliation
and the structural findings, because the script has no file access and agents are called with a string. Later prompts
(profile, synthesis, three synthesis verifiers) embed all four reports again plus the profile/synthesis.
Measured with fake reports of 12,000 chars each (an assumption; I do not know real report sizes): maximum prompt
50,778 chars (a synthesis verification); 19 calls totalled 534,816 chars of prompt (about 27 KB average), i.e. roughly
100-250 KB of text for a realistic run if reports are 12-30 KB. Per prompt the rule of thumb is
about 4 x report size + 2-6 KB. Consequences for `sha256(agent + "\n" + task)`:
- The key is exactly as stable as the report text; any byte change of a report gives a new key for every downstream
  call (this is the wanted invalidation, but it means a corrected report re-asks reconciliation, verification, profile,
  synthesis, as a correct dependency).
- Store size: one `prompt.md` per key, so ~19 files of 1-50 KB per run, ~70 attempts in the recent real run, i.e. a few
  MB. Fine for disk, heavy for the coordinating agent's context if it has to read the prompt file; sub-agents read
  the file, which is the intended design.
- Alternative (not tried): pass a path or short handle and let the host materialize the document, which needs the
  files to be addressable outside the script and the key to carry a content hash. Embedding is simpler and keeps the key honest.

### 6. Differences between one end-to-end run (Pydantic AI) and step replay (bl step)

Expected, not run (I did not have the runners; the step column uses my own replay simulation):
- Identical tasks collide in step mode. Same (agent, task) means the stored answer is reused forever. A correction
  that returns an identical report leaves reconciliation and verification tasks unchanged, so the verifier gets the same
  stored verdict and the loop spins until `MAX_ROUNDS` and raises. In Pydantic AI each call is a fresh sample, so it
  could converge. Failure text changes the key on check-driven retries, so those are fine; verdict-driven corrections rely
  on the corrected text differing.
- Failures. `fail KEY` becomes `RuntimeError` inside the script at that call; my script does not catch it. In
  `gather`, one failing analyst while siblings are open: Pydantic AI/DynamicWorkflow cancels siblings; the step runner
  semantic for sibling prompts already posted is unspecified in the contract.
- Uncaught `RuntimeError` for out-of-attempts is "uncaught script error, exit 1" in step mode, which is not the same
  as "stopped for the operator, resumable". Needs a distinct runner-level signal.
- Replay cost and order: step mode re-runs the script from the top 17 times for 19 calls; harmless here because the
  script is deterministic (no time, random, or I/O). Any non-determinism or a script edit mid-run would silently
  re-interpret stored answers: the script version is not in any key.
- Call budget: DynamicWorkflow has a shared `max_agent_calls` budget; this workflow needs 19 calls in the minimal
  corrected run and ~70 in a real one, so the runner must raise it.
- Breadth: Pydantic AI runs the gathered calls concurrently; step mode posts them together and the harness decides
  width. `analyst` order of answers does not matter since results are collected positionally.
- Attempt numbers in the manifest are script-level attempts. Pydantic AI's own output-validation retries and the step
  runner's `complete` rejection of invalid answers are invisible to the script; worker/model identity must come from the runner.
- Union output types: the step runner's `complete` must validate with a `TypeAdapter` of the union, not a single model class
  (see the note at the top of `catalog.py`). Unions in `anyOf` form appeared in the generated prompt schema; I did not
  check how runner A renders it for the sub-agent.

## Blockers

None for the port. Open points: the three spec gaps in section 4, positional-argument misuse not caught by the static
checker when agents are passed as values, and the runner contract for union outputs.
